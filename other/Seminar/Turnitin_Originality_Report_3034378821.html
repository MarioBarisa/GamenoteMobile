Aplikacija predstavlja mobilnu inačicu postojeće web aplikacije Gamenote, izrađene u Vue.js-u, a razvijena je s ciljem poboljšanja responzivnosti i korisničkog iskustva web aplikacije na mobilnim uređajima. Detaljno su prikazani ključni zasloni aplikacije (početni zaslon, profil, pretraga, grupe) te funkcionalnosti poput sustava postignuća, optimističnih ažuriranja i lokalnog spremanja korisničkih postavki. ABSTRACT This paper describes the development process of Gamenote Mobile, a mobile application for tracking a user's video game collection, built using the React Native and Expo framework (SDK 54). The application is a mobile counterpart to the existing Gamenote web application, built in Vue.js, and was developed to address performance and responsiveness issues of the web version on mobile devices. The paper covers the technologies and architectural decisions used Expo Router for navigation, the React Context API for state management, Supabase as the backend and database, and the RAWG API as the source of video game data. Key application screens (home, profile, search, groups) are presented in detail, along with features such as the achievement system, optimistic updates, and local storage of user settings. 1. Motivacija i odabir tehnologije Aplikacije za mobilne uređaje već su dugo vremena standard za korištenje raznih servisa i usluga u pokretu. Tijekom zadnjih petnaestak godina, evolucijom mobilnih telefona, to još više dolazi do izražaja. Od društvenih mreža do raznih usluga i mobilnih igara, mobilni telefon (pametni telefon) za većinu korisnika predstavlja point-of-entry u online svijet i svijet pametnih usluga. Korisnici također vole i/ili preferiraju korištenje mobilnih aplikacija iz razloga poput jednostavnosti, brzine te fluidnosti u radu u usporedbi s web aplikacijama. Jedna od najosnovnijih i najrasprostranjenijih primjena mobilnih aplikacija jest ona gdje se tradicionalni web servisi i usluge prilagođavaju mobilnoj primjeni tako da izrađuju svoje mobilne aplikacije/klijente (client app). One nude superiorniji UX (user experience) u odnosu na web servise jer su to lokalni programi čiji je jedini cilj dohvatiti podatke s nekog REST ili sličnog servera i prikazati ih korisniku, dok su UI i ostali elementi već lokalno dostupni. Na taj način aplikacije su obično puno fluidnije i ugodnije za rad u usporedbi s web-aplikacijama ili progresivnim web-aplikacijama (PWA) [15, 14]. Client apps bile su prije nekoliko godina izuzetno popularne za mnoge društvene mreže. Zahvaljujući otvorenim API-jima i jednostavnoj implementaciji, postojale su i brojne third- party opcije. Primjerice, Tweetbot za Twitter (sadašnji X) ili ( slika 1 ) bili su pioniri third- party klijentskih aplikacija. Mnogi korisnici su ih koristili umjesto službenih verzija jer su poboljšavale korisničko iskustvo na razne načine: uklanjanje oglasa, bolji pregled threadova, native UI, manje trackinga i slično. Nažalost, u današnje vrijeme navedene aplikacije izumiru jer se navedenim kompanijama više ne isplati da netko nudi proizvod koji je bolji, ali od kojeg oni ne profitiraju. Aplikacija se zove Gamenote. Web aplikacija Gamenote ima za cilj pojednostaviti praćenje korisnikove zbirke videoigara kroz vrijeme te njihovog statusa (odigrana, pauzirana, planirana…). Aplikacija je napravljena koristeći Supabase kao bazu u koju se dodaju podaci preko RAWG API servisa koji ima sve potrebne detalje o gotovo svim videoigrama ikada. Vue.js i daisyUI koriste se za frontend i daju aplikaciji moderan i vizualno atraktivan stil. Međutim, korištenje navedene aplikacije na mobilnim uređajima nije se tijekom razvoja pokazalo optimalnim. Uočeno je kašnjenje pri učitavanju stranica, slabija responzivnost u odnosu na nativne mobilne aplikacije te veći broj koraka za dodavanje igre u Gamenote. Te su uočene poteškoće bile motivacija za izradu mobilnog klijenta; formalna mjerenja performansi i korisničko testiranje u ovom radu nisu provedena. Gamenote Mobile nastaje kao pokušaj rješavanja tih uočenih problema: putem React Native i Expo frameworka korisnik dobiva nativno sučelje. Arhitekturno se očekuje bolja responzivnost jer se UI komponente ne dohvaćaju iznova kao HTML, već su dio instalirane aplikacije. Usporedna mjerenja latencije i korisničko testiranje nisu dio ovog rada. Korištenjem Expo SDK verzije 54.0.0 omogućeno je korištenje renderiranih native elemenata poput tab bara i ostalih zaslona/modala kako bi korisnik dobio premium i ugodno native iskustvo. Također, korištenje navedenog frameworka pomoglo je razvoju jer se putem Expo Go aplikacije i iOS Simulatora [ 9 ] dobiva hot refresh svih promjena u aplikaciji te se na taj način ubrzava razvoj. Pristup je gotovo isti kao kod razvoja web aplikacije koristeći Vue ili React. Postojala je želja da se aplikacija izradi koristeći Swift + SwiftUI, međutim za to nije bilo vremena. Naime, React Native i Expo koriste TypeScript, što je u biti JavaScript gdje je potrebno deklarirati vrstu varijabli zbog type safetyja. Učenje Swifta bi dodalo novu razinu kompleksnosti jer se tamo drugačije pristupa razvoju, te je zbog vremenskih ograničenja odlučeno ostati pri programskoj paradigmi koja je već dobro poznata. Arhitektura aplikacije Arhitektura aplikacije slojevita je oko četiri stvari koje se u nastavku obrađuju odvojeno: Expo SDK kao razvojno okruženje, navigacija putem Expo Routera, upravljanje stanjem kroz React Context API te lokalno spremanje korisničkih preferencija, točnije postavki. Cilj ovog poglavlja nije opisati svaki ekran, nego objasniti zašto su odabrana baš ta tehnološka rješenja i kako se međusobno povezuju. 2.1 Expo SDK Za izradu ove aplikacije korišten je Expo SDK verzija 54 ( SDK@54.0.0 ) [ 11 ]. Odluka o korištenju Expo okruženja umjesto čistog React Native-a bila je jednostavna. Expo je odmah ponudio velik broj funkcionalnosti koje bi inače bilo potrebno ručno konfigurirati. Expo SDK 54 dolazi s React Native 0.81 Koristeći Expo SDK, razvoj je bio znatno brži jer je većina stvari poput splash screena, ikona [ 2 ], haptičke povratne informacije (haptic feedback na promjeni tabova npr) i rada sa slikama riješena gotovim Expo modulima (expo-splash-screen, expo-haptics, expo- image, expo-symbols) koji su dosta puta već bili uključeni u osnovni expo projekt. Ovo je bilo izrazito korisno jer smanjuje potrebu za dodavanjem brojnih NPM / node paketa jer aplikacija zna postati dosta velika ako za svaku stvar se dodaje novi paket. Također, Expo managed workflow omogućio je fokusiranje na funkcionalnosti aplikacije bez potrebe za provjerom postoji li node paket koji radi navedenu stvar. Ipak, uz sve navedene prednosti, javljali su se problemi s node_modules folderom prilikom dodavanja nečega što nije bilo odmah uključeno u Expo. To je jedna od loših stvari oko React-a ili bilo kojeg JS frameworka koja native rješenja nemaju ili imaju u puno manjoj mjeri ( Kotlin, Swift ). Da je korišten "bare React Native", vjerojatno bi bilo potrebno duplo više vremena za postavljanje projekta i rješavanje build errora. Takav pristup bi značajno i nepotrebno usporio razvoj, jer baš zbog takvih razloga postoji Expo da pomogne i ubrza razvoj mobilnih aplikacija. 2.2 Navigacija Za navigaciju unutar aplikacije korišten je Expo Router (v6), file-based routing sustav napravljen na temelju React Navigationa. Expo Router izabran je iz sljedećih razloga: 1. File-based routing: Umjesto ručnog definiranja navigation stacka, dovoljno je kreirati folder i datoteku i ruta je automatski dostupna. To je puno preglednije, pogotovo kad se ima puno ekrana. 2. Route groups: Korišteni su ( tabs ) za glavne tabove i ( modals ) za modalne zaslone. Ovo omogućuje da sve rute budu organizirane, a da se pritom ne utječe na URL strukturu. Za donji tab bar korišten je NativeTabs [ 3 ] iz paketa expo-router/unstable-native-tabs, koji koristi native iOS i Android komponente za kartice umjesto JavaScript implementacije. To je omogućilo znatno ljepši iOS look & feel s podrškom za SF Symbols ikone te ponašanje minimiziranja tab bara koje je dostupno od iOS 18 nadalje, uz haptic feedback pri promjeni zaslona. Ovo je bio jedan od mojih glavnih uvjeta pri izradi aplikacije. JS tab barovi su obično loše napravljeni i nisu dovoljno responzivni, a s obzirom na to da je cilj bio nativnije i responzivnije sučelje, JavaScript tab bar nije dolazio u obzir. Pretpostavljalo se da bi korištenje ovog API-ja, koji je već nekoliko mjeseci u alpha verziji, moglo izazvati neočekivane nestabilnosti, ali to se nije dogodilo. Naprotiv, imao sam vrlo dobro i konzistentno iskustvo korištenja. Navigacija izgleda ovako: 1. Root Stack: glavni container koji drži tabove, modale i settings screen [ 4 ] 2. Tab Navigator:5 tabova: Home, My Games, Search, Groups, Profile [ 3 ] 3. Stack unutar svakog taba: npr. Home ima listu igara i detail screen [ 4 ] 4. Modali: 7 modalnih ekrana koji se prikazuju preko tabova (dodavanje igre, editiranje, registracija itd.) [ 7 ] 2.3 Upravljanje stanjem Za upravljanje stanjem aplikacije korišten je React Context API. [16 ] Aplikacija ima 4 Context Providera: 1. ThemeProvider: upravlja light/dark modom, s podrškom za system default. Spremanje preferencije u AsyncStorage omogućuje da se korisnikov izbor zapamti nakon gašenja aplikacije. 2. SettingsProvider: drži postavke poput vibrationsEnabled (haptički povratni feedback pri prebacivanju tabova), compactCards (prikaz igara u grid ili listi) i language (jezik aplikacije). 3. AuthProvider: najvažniji provider. Drži informacije o korisniku, sesiji i pruža metode za prijavu, registraciju, odjavu i upravljanje računom. Oslanja se na Supabase auth listener (onAuthStateChange) koji automatski prati promjene sesije. [ 5, 6 ] 4. GroupsProvider: upravlja grupama i vezama igara s grupama. Zanimljivost je da koristi optimistična ažuriranja; kada korisnik doda igru u grupu, UI se odmah ažurira, a tek onda se šalje zahtjev na Supabase. Ako zahtjev padne, error se logga, ali korisnik vidi instant povratnu informaciju [ 8 ]. Osim providera, postoji i jedan custom hook useUserGames() koji je srž većine funkcionalnosti. Ovaj hook dohvaća igre iz Supabasea, nudi CRUD operacije i automatski se brine o tome hoće li korisnik biti prijavljen ili ne. Kad korisnik nije prijavljen, hook vraća placeholder podatke (PLACEHOLDER_GAMES) tako da se aplikacija može normalno koristiti i bez računa, što je bilo važno za prezentaciju i testiranje. Ovo je prvenstveno implementirano kako bi korisnik mogao vidjeti aplikaciju prije nego što potroši vrijeme na izradu računa, odnosno kako bi procijenio sviđa li mu se aplikacija. 2.4 Lokalno spremanje podataka Za lokalno spremanje podataka na uređaju koristi se AsyncStorage. [ 17 ] Iako postoje druge opcije poput Expo SecureStore ili SQLite, bilo je potrebno samo nekoliko jednostavnih key-value parova, pa je AsyncStorage bio logičan izbor za spremanje osnovnih preferencija korisnika i Supabase sesije. Što spremam lokalno: 1. Tema (theme preference): da korisnikov izbor light/dark/system ostane zapamćen 2. Postavke (vibrationsEnabled, compactCards, language): tako da korisnik ne mora svaki put podešavati iste stvari 3. Onboarding status: flag koji označava je li korisnik već vidio uvodni onboarding modal. Korisnik će samo jednom vidjeti navedeni, točnije jedini način da ga na istom uređaju opet vidi je da ponovno instalira aplikaciju. 4. Supabase sesija: korisnik se ne mora ponovno prijavljivati svaki put kad otvori aplikaciju Važno je napomenuti da se glavni podaci (igre, grupe) ne spremaju lokalno oni se uvijek dohvaćaju sa Supabase servera. Aplikacija zahtijeva internet za potpunu funkcionalnost. Ovo je napravljeno namjerno jer je cilj da korisnik ima svoje podatke sinkronizirane na svim uređajima, a ne samo na jednom (više Gamenote mobile aplikacija + web ). AsyncStorage je ovdje poslužio samo kao cache za postavke, a ne kao baza podataka. Cilj nije bio izraditi offline-first aplikaciju, nego aplikaciju koja se oslanja na server, ali pamti korisničke preference lokalno. Autentifikacija i korisnički put Autentifikacija u aplikaciji nije odvojeni „login screen“, nego sloj koji određuje što korisnik vidi i koje podatke aplikacija smije dohvatiti. U ovom poglavlju opisan je odabir Supabasea, način na koji se sesija drži u stanju aplikacije, uvodni tok za novog korisnika te zaštita ruta. Posebno je bilo važno da se aplikacija može pregledavati i bez računa, pa je korisnički put namjerno podijeljen na demo način rada i rada s pravim podacima točnije prijavljenim korisnicima. 4.1 Arhitektura autentifikacijskog sustava Za backend autentifikacije odabran je Supabase, open-source platforma koja je pružila gotovo sve spremno za rad: registraciju, prijavu, upravljanje sesijama i PostgreSQL bazu podataka, a sve to bez potrebe za vlastitim serverom. Supabase koristi JWT tokene za autentifikaciju, a u React Native okruženju pohranjeni su u AsyncStorage putem @react- native-async-storage/async-storage, što omogućuje da sesija preživi gašenje aplikacije. Konfiguracija je prilično jednostavna, ali zahtijeva nekoliko ključnih postavki autoRefreshToken mora biti true da se tokeni osvježavaju u pozadini, persistSession omogućuje trajnost sesije, a detectSessionInUrl je postavljen na false. Cijeli autentifikacijski sloj podijeljen je u tri razine: na najnižoj je supabase.ts koji samo stvara i eksportira Supabase klijent, iznad njega je supabaseAuth.ts koji omata sve auth operacije i prevodi greške, a na vrhu je AuthContext unutar context/auth.tsx koji cijelo stablo komponenti opskrbljuje stanjem autentifikacije. 4.2 Upravljanje stanjem autentifikacije AuthProvider [ 5 ], postavljen u korijenskom layoutu aplikacije (layout.tsx), odgovoran je za nekoliko ključnih stvari. Prilikom mountanja, on prvo pokušava dohvatiti postojeću sesiju iz Supabasea pozivom supabase.auth.getSession(), i ako sesija postoji, osvježava podatke o korisniku s supabase.auth.getUser(). Zatim se pretplaćuje na onAuthStateChange događaj koji ga obavještava o svakoj promjeni; prijava, odjava, osvježavanje tokena i na temelju toga ažurira stanje. Dok se ta inicijalna provjera odvija, isLoading je postavljen na true, a korisnik vidi splash screen s indikatorom učitavanja, tako da nema ružnih bljeskova ili trenutaka kada aplikacija ne zna što bi sama sa sobom. 22 Stanje autentifikacije svedeno je na jednu boolean varijablu loggedIn, koja je izvedena iz !! session i na nju se oslanjaju sve komponente i hooks u aplikaciji. 4.3 Prvo pokretanje i uvodni zaslon Prvi put kada korisnik otvori aplikaciju, dočekuje ga onboarding modal postavljen da se prikaže točno jednom i to isključivo za neautentificirane korisnike. Nakon što se tabovi učitaju, u (tabs)/layout.tsx provjerava se je li korisnik prijavljen i, ako nije, provjerava se AsyncStorage ključ @onboarding_complete. Ako ga nema, s kašnjenjem od 300 milisekundi ( čisto da se tabovi prvo stabilno prikažu ) otvara se onboardingModal na zaslonu. Unutar tog modala korisnik vidi veliki Gamenote logo, dobrodošlicu i četiri feature carda koji kroz SF Symbols vizualno objašnjavaju što aplikacija nudi; spremanje i praćenje igara, ocjenjivanje i recenziranje, organizaciju u grupe te praćenje statistike. Dno modala donosi "Continue" gumb koji vodi direktno na profile tab, a pri dnu su verzija aplikacije i podaci o developeru ( meni ). 4.4 Prijava i registracija Prijava je implementirana direktno ( Slika 27 ) korisnik unese email i lozinku, pritisne gumb, i signIn funkcija iz AuthContexta prosljeđuje zahtjev Supabaseu. U slučaju greške, korisnik dobiva poruku (primjerice "Neispravan email ili lozinka”) [ 8 ], a u slučaju uspjeha sesija se pohranjuje, loggedIn postaje true, i root index (app/index.tsx) odmah preusmjerava korisnika na home tab. Registracija je složenija. registerModal otvara se kao modal preko trenutnog zaslona, s poljima za korisničko ime, email, lozinku i potvrdu lozinke. Lozinka ima toggle za prikazivanje/sakrivanje teksta putem SymbolView i eye.fill/eye.slash.fill ikonica, što je jedna od onih sitnica koje korisnik možda ni ne primijeti svjesno, ali čine iskustvo ugodnijim. Validacija je stroga. E-pošta prolazi kroz regex provjeru formata, lozinka mora imati minimalno 8 znakova i barem jedan broj ili kombinaciju velikog i malog slova, a potvrda se mora podudarati. 4.5 Zaštita ruta i upravljanje pristupom Umjesto klasičnih route guarda ili middlewarea koji bi se možda koristili u web aplikacijama, ovdje je odabrano nešto što se smatra jednostavnijim rješenjem u React Native okruženju komponentnu uvjetnu renderaciju. Slika 28: Prikaz svih izrađenih ikona 5.1 Prijevod i lokalizacija Za podršku engleskome i hrvatskome korišten je i18n. Cijeli sustav temelji se na react- i18next biblioteci, gdje su svi tekstualni resursi organizirani u dvije JSON datoteke: hr.json i en.json s hrvatskim kao osnovnim jezikom (fallbackLng: "hr"), što znači da ako neki prijevod na engleskom nedostaje, aplikacija se vraća na hrvatski umjesto da prikaže prazninu ili ključ. Ključna odluka koja je donesena bila je grupiranje svih prijevoda po logičkim cjelinama unutar JSON strukture common za univerzalne stvari poput "Spremi" ili "Odustani", profile za profil, register za registraciju, settings za postavke i tako dalje. Svaka komponenta u aplikaciji zatim poziva t('profile.logout') ili t('register.passwordLength'), što znači da dodavanje novog jezika (primjerice njemačkog) ne zahtijeva nikakve izmjene koda samo novu JSON datoteku i dodavanje u SUPPORTED_LANGS. Detekcija jezika radi automatski pri pokretanju, učitava se localeIdentifier iz I18nManager i ako počinje s "hr", postavlja se hrvatski, inače ( za bilo koji drugi jezik ) engleski. Korisnik kasnije može promijeniti jezik u postavkama, a preferencija se pohranjuje u AsyncStorage. 6. Distribucija Distribucija aplikacija na platformi iOS odvija se putem službene trgovine aplikacija App Store. Od sredine 2024. godine uvedene su i alternativne „tržnice aplikacija“ nakon što je Apple pod regulatornim pritiskom Europske unije bio primoran implementirati iste. Primjeri alternativnih tržnica su SetApp i AltStore PAL. Za objavu aplikacije na bilo koji službeni izvor (App Store ili alternativu) distribucije potrebno je ući u Apple Developer program koji košta 99 USD godišnje. Međutim, zbog napretka AI tehnologije Apple je postao znatno stroži u odobravanju novih Developer računa, vjerojatno u svrhu prevencije „poplave“ App Storea niskokvalitetnim, „vibe-coded“ aplikacijama koje stvaraju osobe bez dovoljnog tehničkog znanja. Pokušao sam se prijaviti u navedeni program i već dva tjedna nema napretka prema rješenju. Ovo predstavlja problem jer objavljivanje na App Storeu daje aplikaciji kredibilitet i otvara mogućnost monetizacije. Postoji ideja o pozicioniranju Gamenote Mobile kao premium aplikacije za koju bi se plaćao jednokratni iznos od 4,99 EUR. Na taj bi način korisnik dobio premium iskustvo korištenja Gamenote servisa u slučaju da mu web verzija nije dovoljna. Na isti način moguće je monetizirati aplikaciju bez preplavljivanja godišnjim pretplatama ili drugim predatorskim modelima naplate. 6.1 Izrada IPA datoteke i instalacija Uz sve navedeno, aplikacija je distribuirana na klasičan iOS sideloading način. Sideloading je naziv za proces instalacije aplikacije iz izvora koji nije Apple odobrio za distribuciju. Za navedeno bila je potrebna IPA datoteka. Ona je zapravo samo zapakirani kod aplikacije, sličan .exe ili .apk formatu, ali za iOS uređaje. Prvi korak bio je izrada Gamenote.xcodeproj datoteke putem službenog Expo CLI alata, koja je zatim otvorena u službenom Apple IDE-u za razvoj na njihovim platformama Xcode 26.5 [ 9 ], [ 10 ]. Ovdje je bilo potrebno odabrati besplatni dev račun kao originalnog autora te odabrati target iOS verziju. Odabrana je iOS 18 i novije verzije jer većina korisnika ne koristi starije iOS verzije. Nakon toga pokrenuto je kompajliranje IPA datoteke, koje je trajalo nekoliko minuta. Kada je dobivena iOS datoteka, bio je potreban način njezine instalacije na telefon. Ovdje postoji nekoliko popularnih alata: AltStore Classic i Sideloadly. Odabran je AltStore Classic iz nekoliko razloga: 1. Automatska obnova certifikata kada su računalo i telefon na istoj Wi-Fi mreži. 2. Mogućnost dodavanja izvora – ako u bližoj budućnosti ne dobijem Developer račun, mogu napraviti vlastiti izvor (link) na sve svoje aplikacije i na taj način korisnicima davati OTA ažuriranja. 3. Jednostavnost korištenja. 4. Reputacija – AltStore je prisutan već desetak godina. Važno je razlikovati AltStore Classic i AltStore PAL. AltStore PAL je službena alternativna tržnica aplikacija koja je odobrena od strane Applea, za razliku od AltStore Classica koji to nije. Također, PAL verzija je dostupna isključivo unutar Europskog ekonomskog područja (EEP), dok se Classic verzija može instalirati bilo gdje. Proces počinje na računalu, gdje je potrebno instalirati AltServer koji služi za inicijalnu instalaciju, a kasnije i za obnavljanje potpisa aplikacije. Tijekom procedure korisnika se pita za Apple ID i lozinku. Važno je napomenuti da se ti podaci šalju isključivo Appleu te da ih nitko drugi ne vidi, koriste se samo za stvaranje potpisa aplikacije. Naime, svaka aplikacija ima potpis koji daje developer (u ovom slučaju ja). Kod besplatnog developerskog računa potpis traje 7 dana, umjesto jedne godine kod plaćenog računa. To je glavno ograničenje koje AltStore pomaže ukloniti, ako su računalo na kojem je instaliran AltServer i uređaj s AltStoreom na istoj Wi-Fi mreži, obnova certifikata odvija se automatski, bez potrebe za intervencijom korisnika. Nakon instalacije u AltStoreu treba samo odabrati GamenoteMobile.ipa i provjeriti da je Wi-Fi mreža ista kao na računalu (ili spojiti uređaj kabelom) nakon toga je aplikacija instalirana. Zaključak U ovom radu prikazan je proces izrade mobilne aplikacije Gamenote Mobile, razvijene korištenjem React Native i Expo frameworka (SDK 54), kao mobilnog pandana postojećoj web aplikaciji Gamenote izrađenoj u Vue.js-u. Motivacija za izradu proizašla je iz kvalitativno uočenih problema sporosti, slabe responzivnosti i kompleksnog korisničkog iskustva web verzije na mobilnim uređajima. Tijekom razvoja korištena su arhitekturna rješenja poput Expo Routera za file-based navigaciju, React Context API-ja za upravljanje stanjem (Theme, Settings, Auth, Groups), Supabasea kao backend i autentifikacijskog sloja, te RAWG API-ja kao izvora podataka o videoigrama. Implementirani su svi ključni ekrani aplikacije, uz dodatne funkcionalnosti poput sustava postignuća, optimističnih ažuriranja i lokalnog spremanja korisničkih postavki. U odnosu na početnu motivaciju, implementirano je nativno sučelje i smanjen je broj koraka za uobičajene radnje. To se u radu obrazlaže arhitekturom i tijekom korištenja u razvoju, a ne formalnim mjerenjima performansi ni testiranjem na korisnicima. Korištenje Expo frameworka pokazalo se ispravnom odlukom jer je ubrzalo razvoj i omogućilo fokus na funkcionalnosti umjesto na konfiguraciju build sustava. Tijekom razvoja naišao sam i na nekoliko prepreka nestabilnost modula expo-image-picker na iOS 18.5 uređajima, zbog čega je promjena profilne slike riješena unosom direktnog linka, te otežan pristup Apple Developer programu, koji je usporio distribuciju putem App Storea. Zbog toga je aplikacija privremeno distribuirana sideloading metodom putem AltStore Classica. Iako aplikacija u sadašnjem obliku ispunjava postavljene ciljeve, postoji prostor za daljnji razvoj proširenje zaslona postavki (npr. prilagodba accent boje), rješavanje problema s expo-image-pickerom te, ako mi to bude dopušteno, objava aplikacije na App Storeu kao premium proizvod. Ovaj projekt omogućio je dublje razumijevanje razvoja mobilnih aplikacija putem React Native i Expo frameworka, kao i razlika u pristupu razvoju mobilnih i web-aplikacija.
